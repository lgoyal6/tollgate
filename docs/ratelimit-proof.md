# Proof: distributed rate limiting is correct across replicas (and the naive version is not)

Date: 2026-07-27. Environment: kind cluster (single node) on an Apple M-series
laptop, 3 gateway replicas behind one Service, shared Redis and Postgres
provisioned by Terraform. Load generated by k6 on the same host through
kind's NodePort mapping.

## Setup

- Tenant `metered`: sliding window log, **limit 300 requests / 1s window**
  (`tenants.rl_algorithm='sliding_window', rl_limit=300, rl_window_ms=1000`).
- Offered load: constant arrival rate of **1,200 req/s for 30s** (4× the
  quota), `loadtest/correctness.js`.
- The Kubernetes Service spreads connections across all 3 gateway pods; each
  pod makes its own admission decisions.
- Admission ceiling over the run: `300 × (30 + 1) = 9,300`
  (one extra window of slack for boundary overlap).

The only variable changed between the two runs is the Helm value
`limiter=memory|redis` (`scripts/demo-distributed-vs-memory.sh` performs the
redeploys and both runs).

## Results

| | naive in-memory limiter | Redis Lua limiter |
|---|---|---|
| admitted (HTTP 200) | 26,942 | **9,000** |
| rejected (HTTP 429) | 9,058 | 27,001 |
| other/errors | 0 | 0 |
| ceiling | 9,300 | 9,300 |
| over ceiling | **+189.7%** | −3.2% |
| globally correct | ✗ | ✓ |

Raw output: `loadtest/results/correctness-memory.json`,
`loadtest/results/correctness-redis.json`.

## Reading the numbers

- **Memory limiter admitted ~2.9× the quota.** Each of the 3 replicas kept
  its own window and independently admitted up to 300/s. 26,942 ≈ 3 × 9,000
  (connection distribution across pods isn't perfectly even, hence not
  exactly 3×). A tenant paying for 300 req/s would silently receive ~900  - 
  and the multiplier grows with every scale-out event, which is exactly
  what an HPA does under load.
- **Redis limiter admitted 9,000 = 300/s × 30s, exactly.** All replicas
  share one ZSET per tenant, and the check-and-insert runs as a single Lua
  script inside Redis's execution thread, so concurrent replicas cannot
  both consume the same slot. It landed *under* the 9,300 ceiling because
  the ceiling's +1 window is deliberate slack for boundary overlap, not a
  target.

## Corroborating evidence at the unit level

`internal/ratelimit/redis_test.go` (`TestRedisAtomicityUnderConcurrency`)
drives 20 goroutines × 50 requests at one tenant against a real Redis:

- sliding window, limit 100: admitted **exactly 100** of 1,000;
- token bucket, burst 100 @ 50/s: admitted 103 against a computed
  elapsed-time ceiling of 108 (refill during the 60ms run).

## Why the scripts are trustworthy

- Single Lua script per decision - Redis executes scripts serially, so
  read-modify-write is atomic without locks or transactions.
- Clock source is Redis `TIME` inside the script: one authoritative clock
  for all replicas; gateway clock skew is irrelevant. (Redis ≥ 5 replicates
  scripts by effects, so calling TIME before writes is replication-safe.)
- Sliding-window ZSET members are `<microsecond>-<request-id>`, so two
  replicas admitting in the same microsecond still insert two members.
- `redis.Script` uses `EVALSHA` with automatic `EVAL` fallback: steady-state
  overhead is one round trip carrying a 40-byte SHA.
